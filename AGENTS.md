# Project agent instructions

- Do not use the Codex in-app browser for verification, visual QA, or local web testing in this repository unless the user explicitly requests it in a future message.
- Prefer automated tests, type checks, linting, production builds, and non-browser inspection for verification.
- Run all backend Python commands in the project virtual environment. On Windows, use `backend\venv\Scripts\python.exe` from the repository root or `.\venv\Scripts\python.exe` from `backend` for Django management commands, pytest, scripts, and package operations; do not use the system Python interpreter.

## Application integration: scrolling and mobile layout

- Before integrating or changing an application page, trace its actual route through `ApplicationShell` / `MainLayout` and identify which element owns scrolling. In `frontend/src/styles/global.css`, `body`, `#root`, and `.app-main` intentionally use `overflow: hidden`; the root/layout are viewport-height containers. Only `.app-main--padded` provides shell-owned vertical scrolling. `fullBleed` removes that behavior as well as padding; embedded views also use this behavior.
- For a document-style application (forms, cards, lists, long content) inside a full-bleed shell, put the shared `app-scroll-page` class on its page root, alongside its own class. This utility lives in the eagerly loaded global stylesheet and provides `width: 100%`, `height: 100%`, `min-width: 0`, `min-height: 0`, and `overflow-y: auto`. Examples: `KitchenAssistantPage` and `ResearchAssistantPage`. Do not override those bounds with `height: auto` in mobile rules. Spacing and `max-width` alone do not create a scroll container.
- For editors, chat, canvases, terminals, or other pane-based workspaces, keep the intended pane as scroll owner instead of blindly adding page-level scrolling. Carry a bounded height through intermediate wrappers, use `min-height: 0` / `min-width: 0` on shrinking flex/grid items and `minmax(0, 1fr)` for constrained tracks, then set `overflow-y: auto` on the appropriate content pane. Recheck the scroll owner when mobile breakpoints stack desktop columns.
- Size embedded application roots from their parent (`height: 100%`), not another `100vh` / `100dvh`: the shell already reserves space for headers, toolbars and mobile navigation. Include safe-area padding where needed so the final item and actions remain reachable. Adding only `overflow-y: auto` without constraining the height is insufficient.
- Do not fix one application's scrolling by globally unlocking `body`, `#root` or `.app-main`, or by adding document-wide touch handlers. This can break other full-height workspaces and create nested scrolling. Check ancestor overflow, height bounds and flex/grid minimum sizes before investigating `touch-action` / `preventDefault`. Normal content must retain vertical touch panning and pinch zoom; isolate special gesture handling to the controls that need it.
- Inspect long-content states in every tab plus loading/error states, long forms in modals/drawers, and mobile stacked panes. Account for `entry=home`, `entry=apps`, `standalone=1` and `embedded=1`, because their available heights and navigation differ. Check phone widths (320/375/390px), the 767/768px shell boundary, desktop layout, and short landscape viewports.
- Add a regression check for each new full-bleed application's scroll contract in `frontend/src/layouts/__tests__/mobileScrolling.test.ts` (or a focused layout test), including page-root attachment and responsive height/overflow overrides. DOM interaction tests in jsdom do not perform layout and cannot prove touch scrolling, even when all functional tests pass. Use CSS/layout inspection and automated checks under the existing no-in-app-browser rule; clearly distinguish those checks from real-device/browser verification. Never claim mobile scrolling was visually verified without actually verifying it in an authorized environment.

## Application UI refinement: lessons from Douyin Benchmark

- Trace the rendered component before editing a screenshot's UI. `DouyinBenchmarkPage.tsx` owns the application entry and account library, while `douyin/DouyinWorkspace.tsx` renders the account workspace and work cards; both use `DouyinBenchmarkPage.css`. Check shared selector consumers and existing local changes before modifying them.
- Fix information hierarchy before adding decoration: separate account identity and account actions, collection controls, navigation, filters, sample context, and work results. Within each work card, distinguish publication metadata, title, interaction metrics, source links, and actions. Give the main action visual priority and keep secondary or destructive actions quieter without hiding them.
- Scope layout rules to explicit field wrappers rather than all descendant `label` elements. Ant Design checkboxes also render a `label`; applying `display: grid` to every toolbar label separated the checkbox from its text and created excessive whitespace. Prefer dedicated field classes, or exclude `.ant-checkbox-wrapper` where a shared label rule is necessary. Check component-library structure and selector specificity when diagnosing alignment issues.
- Give filters visible labels associated with their controls, rather than relying only on placeholders. Keep checkbox controls and their text aligned with inline flex. Preserve accessible names, keyboard focus indicators, and existing action behavior when adding icons; use the page's existing icon family and mark decorative icons `aria-hidden`.
- Reflow work cards deliberately on narrow screens: let filters stack, keep long titles readable, move metrics and actions onto full-width rows, and reduce metric columns when numbers become cramped. Use shrinkable grid tracks and children, explicit cover aspect ratios, and wrapping for user-generated text. Keep mobile controls comfortably tappable; do not solve overflow by clipping content or shrinking all text.
- Reuse semantic theme variables for surfaces, borders, text, and emphasis. Check actual foreground/background contrast in both light and dark themes, including secondary text. Present interaction values with explicit labels and tabular numerals; retain missing-data states and sample explanations. Any new summary must come from real response fields with an accurate scope, such as effective sample size or median likes, rather than implying account-wide totals or future performance.
- Validate UI refactors with existing workflow tests, targeted linting, type checks, and a production build. When changing responsive layout contracts, extend the CSS/layout regression checks to cover filter columns, card reflow, checkbox alignment, and the existing scroll owner at relevant breakpoints and short heights. Report these as automated/static checks, not visual verification; a passing build or jsdom test does not establish rendered appearance.
